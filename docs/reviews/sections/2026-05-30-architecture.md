# Architecture & Standards Review — 2026-05-30

## Summary

- **Largest standards-drift surface is the legacy `Promise<{ success, error? }>` return shape (NEVER-DO #19 spirit)** — 17 server-action files still use this instead of `ActionResult<T>`, including `liaison-actions.ts` (524 LOC, every export), `finance-actions.ts` (`createInvoice`/`recordPayment`/etc.), `proposal-actions.ts`, `project-step-actions.ts`, `inventory-actions.ts`, `leads-actions.ts`. The shape is structurally similar but loses the `code` field, the discriminated-union ergonomics, and the documented `ok()`/`err()` helpers. New code is mostly compliant; this is technical debt in the old surfaces.
- **NEVER-DO #12 (no JS aggregation over money) is violated on multiple hot paths.** `closure-actions.ts:86-89` reduces BOM cost to compute the green/amber/red margin band that gates lead-to-won transitions — the most safety-critical money path in the system. `po-actions.ts:77-78` recomputes PO subtotal+GST from a JS reduce instead of an SQL trigger/RPC. `project-detail-actions.ts:325-335` reduces BOQ and expense rows to compute project actuals. `payments-overview-queries.ts:206-208` and `pm-queries.ts:91,142-152` reduce active-project rows on the dashboard path. `partners-queries.ts:336-337` reduces commission payouts on every partner-summary load.
- **NEVER-DO #16 violation still latent:** `plant_data_readings` (`supabase/migrations/005d_om.sql:522`) is the legacy 15-minute Sungrow/Growatt telemetry table — non-partitioned, no rollup table. The new `inverter_readings` (mig 050) was built correctly; the old table appears to still take writes from the old `plant-monitoring-*` code paths.
- **Recent SQL drifts from the helper-function discipline:** migrations 138 + 139 (the Wave 1-4 AI features, just shipped) use raw `EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND role = ...)` inside their RLS policies — exactly the pattern master ref §5.6 says infinitely recurses. Should use `get_my_role()` / `get_my_employee_id()` from mig 008a.
- **`as any` is still widely used despite NEVER-DO #11.** 196 occurrences across 31 files inside `apps/erp/src/lib`. `liaison-actions.ts` alone has 15, `project-step-actions.ts` has 62. Most are `.insert(... as any)` / `.update(... as any)` patterns that mask schema-drift risk and bypass the regenerated-types discipline rule #20 was built to enforce. (None match the `from(table as any)` or `select(... as any)` regex the CI baseline catches; this is the broader spirit of the rule.)
- **Migration filename collision unresolved.** Two files at `supabase/migrations/115_*.sql` (`115_liaison_tneb_stages.sql` and `115_referrer_consolidation.sql`); mig `124` is missing entirely. This was called out in the 2026-05-24 comprehensive review and has not been corrected.

- Replace `getLeadTasks` (`leads-task-actions.ts:224-242`) `throw` with `return { data, error }` or `ActionResult`. Single function, one caller.

- Replace `EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND role IN (...))` with `get_my_role() IN (...)` in migs 138 + 139. Pure SQL substitution; the helpers are unchanged since mig 008a.
- Replace 7 `as any` casts in `contacts-actions.ts` with `ContactInsert`/`ContactUpdate` row types. Tests will catch.

## Needs Vivek review (judgment calls)

- **Whether to keep `plant_data_readings` (`005d_om.sql:522`) at all.** The newer `inverter_readings` (mig 050) was built specifically to replace it with proper partitioning. If old `plant-monitoring-actions.ts` writes have been retired, the table can be archived; if they're still active, partitioning is mandatory before scale hits.
- **Bulk-converting all 17 legacy-shape action files to `ActionResult` in one sweep vs. file-at-a-time as they're touched.** Big-bang has merge-conflict risk; incremental keeps the divergence visible for months.
- **Refactoring `project-step-actions.ts` (2522 LOC, 62 `as any`).** This file accumulates anything project-stepper-related. Splitting it into 5-7 sub-files would help maintainability but creates a non-trivial merge surface for in-flight work.
- **The JS-aggregation issues in `closure-actions.ts` and `po-actions.ts` are HIGH severity but require new SQL RPCs to fix correctly.** Fixing them inline (cleaner JS, same architecture) would unblock more than half the NEVER-DO #12 surface without needing migrations; full-fix is correct per master ref but slower.
- **`createAdminClient` use in `vendor-bills/[id]/page.tsx:32`.** It's gated behind `ai_status === 'pending_review'` and only used for storage signed-URL generation. Strict reading of NEVER-DO #15 says move it out; pragmatic reading says it's a one-line use that already has an AI-status gate. Founder call.
- **Whether to ratchet the forbidden-pattern baseline to catch broader `as any` usage** (currently only catches `from('x' as any)` and `select('...' as any)`). A broader regex would catch the 196 occurrences but would also block legitimate cases like the `(project as any).system_size_kwp` accessor pattern where the underlying type is JSONB or computed. Decision: do or don't tighten the regex.
- **n8n `ErpEventName` union vs router Switch coverage** — fix the mismatch by trimming the union (smaller surface, less optionality) or by adding the missing router cases (more discoverability, more workflows to maintain). Affects which mental model is canonical: ERP-side type-defined events vs. router-defined event taxonomy.
