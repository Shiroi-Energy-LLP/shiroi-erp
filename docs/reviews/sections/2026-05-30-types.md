# Type Safety & DB Query Correctness Review — 2026-05-30

## Summary

- **`pnpm check-types` currently passes — but that means nothing.** The 196 `as any` casts across `apps/erp/src/lib` are actively hiding real schema mismatches. The single most damaging case: `project-step-actions.ts:761-768` inserts into `project_profitability` using four non-existent column names (`total_estimated_cost`, `total_actual_cost`, `estimated_margin_pct`, `actual_margin_pct`) and also omits the NOT-NULL `total_revenue` column — every call to `addCostVariance` runs this insert when the row doesn't exist yet, and every call returns "column does not exist" at runtime. The `as any` cast at line 768 is the only reason `check-types` doesn't catch it.
- **CHECK-constraint violations on the `notifications` table are widespread.** Migration 014 restricts `notification_type` to `{alert, reminder, report, approval_required, info}` and `entity_type` to `{proposal, project, lead, purchase_order, daily_report, employee, override_report}`. The application inserts `'closure_approval'`, `'procurement'`, `'po_pending_approval'`, `'po_approved'`, `'po_rejected'`, `'rfq_quote_submitted'` for `notification_type`, and `'rfq'` for `entity_type`. Every one of these inserts returns a 23514 check_violation, and most code paths silently swallow it (no error destructuring on the `.insert()` call). Net effect: founders never get PO approval pings, RFQ creators don't learn quotes have arrived, marketing-manager amber-band closures don't notify founders.
- **Three RPC names called from the app don't exist as DB functions.** `get_referral_commission_this_month` and `get_referral_commission_lifetime` (`referral-queries.ts:21,29` — called with `as never` to suppress the type error) are never defined in any migration; the /referrals KPI strip always shows ₹0 for both. `increment_boq_dispatched_qty` (`project-step-actions.ts:1095`) is called with `as any`; it doesn't exist either, so every delivery-challan creation runs the rpc, ignores the error, and falls through to the manual JS update that follows — effectively dead first call + redundant second call. These were missed by the prior review.
- **The handover-pack BOM lookup uses two non-existent column names on `proposal_bom_lines`.** `handover-actions.ts:46-47` looks for `l.category === 'panels'` and `l.item_name?.toLowerCase()` — the real columns are `item_category` and `item_description`. Both `.find()` calls return undefined every time, so every handover document shows "As per BOM" for panel brand and "—" for panel model. Customer-facing PDF is structurally wrong.
- **`get_msme_due_count` exists in mig 028 but is not in `database.ts`.** Called by `finance-queries.ts:64`. The function works at runtime, but the typegen output is stale — same root cause as the prior review's "regenerate types" finding. Several other functions (`generate_doc_number`, `get_referral_commission_*` if they were to be added) sit in the same gap.
- **The legacy `Promise<{ success, error? }>` action shape combined with merged `if (error || !data)` checks weakens error reporting in 15 files** — Supabase distinguishes "row not found" from "query errored" via separate `error` and `data` fields, and the merged check collapses them into a single "Failed" message that loses the DB error code. Master ref §4.1 mandates separate checks.

## Needs Vivek review (judgment calls)

- **Notification CHECK constraint vs caller code mismatch.** Two ways to fix: (a) expand the mig 014 CHECK to allow the new types (`closure_approval`, `procurement`, `po_pending_approval`, `po_approved`, `po_rejected`, `rfq_quote_submitted`, plus `rfq` on entity_type), regen `database.ts`, then everything works. (b) Rewrite every caller to use the existing 5 values (`approval_required` for pending stuff, `info` for outcome announcements). Option (a) is one migration + one type regen but adds permanent enum surface; option (b) is 7 caller-site edits that lose granularity in the UI ("you have an approval_required" doesn't tell the user what kind). Founder call on which side to bend.
- **The three missing RPCs (`get_referral_commission_this_month`, `get_referral_commission_lifetime`, `increment_boq_dispatched_qty`).** Worth implementing in SQL, or are the in-app paths sufficient? Referral KPIs definitely need the data; the dispatched-qty manual update arguably wants atomicity guarantees.
- **Whether to ratchet the forbidden-pattern baseline to catch `(x as any)` accesses.** The 196 occurrences include both genuine type bugs (the project_profitability case above) and pragmatic narrow-casts after `.maybeSingle()`. A broad regex would block legitimate uses. A targeted regex for `\.from\([^)]+\)\s*\.(insert|update)\([^)]+ as any\)` would catch the most damaging cases (where the cast hides column-name drift on writes).
- **Money math in JS in `procurement-actions.ts`, `rfq-actions.ts`, `finance-actions.ts`, `po-actions.ts`.** Fixing inline with `Decimal` is fast; the proper fix (per master ref §4.5) is SQL RPCs that recompute totals from line items, but that's a multi-week refactor. Recommend Decimal as a stopgap, mark a tech-debt ticket for the RPC migration.
- **Stale `database.ts` regen.** `get_msme_due_count` is the visible symptom; there may be more (any function added pre-typegen-skip). Worth doing a fresh regen + commit even if no schema changed today, to flush out hidden gaps.
- **`notifications-queries.ts` no-scope queries.** Adding `.eq('recipient_employee_id', employeeId)` requires the caller to pass the id, which changes 4 call signatures. Alternative: have the functions resolve `employeeId` themselves from `auth.uid()`. Cleaner but adds one query per call. Founder pick.
