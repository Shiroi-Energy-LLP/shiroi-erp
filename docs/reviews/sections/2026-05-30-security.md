## Summary

**Top issue is a full-blown privilege-escalation hole** in
`employee-actions.ts` — `createEmployeeAccount` and `deactivateEmployee`
are 'use server' actions that hold the admin client, accept role/email
input, but never check the caller's role. The page wrapper at
`/hr/employees/new/page.tsx` gates with `requireRole(['founder',
'hr_manager'])`, but server actions can be invoked directly via HTTP —
the page check is not the action check. Any authenticated user can POST
to `createEmployeeAccount({ role: 'founder', ... })` and own the org.

Beyond that, the biggest pattern problems are: (a) **PostgREST `.or()`
filter injection** in ~15 search queries that string-interpolate the
search term into the `or()` filter expression, (b) the `process-document`
Edge Function accepts unauthenticated POST and burns Claude+Jina quota,
(c) the `/api/contacts/search` API route has no auth gate (relies on
cookie middleware refresh, not enforcement), (d) several SECURITY DEFINER
functions in older migrations are missing `SET search_path` or role
gates (mig 132's `get_salary_benchmark_report` is missing `search_path`,
mig 008a's `get_my_role()` is granted to `anon`), and (e) the customer
proposal portal logs the client IP into the DB but doesn't actually
rate-limit or rotate tokens after a suspect view.

The recent hardening migrations (134 RLS / 135 PO-recon gate / 136 leave
RPC + attendance check / 137 DC-cert immutability + liaison gate + proposal
sanity) closed all the issues from the 2026-05-24 review and the migration
pattern shown there (SECURITY DEFINER + role gate + `SET search_path`) is
exactly right — the older functions just haven't been audited.

## PostgREST `.or()` injection — additional locations

Pattern: `query.or(\`field.op.${userInput}\`)` where `userInput` comes from
`filters.search` or request body. PostgREST escapes values within an op
expression, but a value containing `,` or `(` breaks out of the current
clause and into a new OR term. Affects (`(erp)/src/lib` paths):

- `contacts-queries.ts:45, 125, 168` — name/phone/email/city/gstin filters
- `data-review-queries.ts:84, 111, 167` — customer_name / project_number / notes
- `invoice-queries.ts:35` — invoice_number
- `inventory-queries.ts:119` — item_description / brand / serial_number
- `leads-queries.ts:83` — customer_name / phone
- `orphan-triage-queries.ts:205` — customer_name / project_number
- `partners-queries.ts:43` — partner_name / contact_person / phone
- `payment-queries.ts:14` — payment_reference / receipt_number
- `plant-monitoring-queries.ts:61` — username / notes (sensitive — exposes inverter credentials by name)
- `procurement-actions.ts:707` — company_name / contact_person
- `project-detail-actions.ts:284` — name / phone / email
- `proposals-queries.ts:48` — proposal_number
- `app/api/whatsapp/voice-report/route.ts:282` — employee.id interpolation (lower risk since employee.id is from a trusted lookup, not user input)

Fix: use `query.or(\`name.ilike.${literal}\`)` where `literal` is a
sanitized version of `%${search.replace(/[,(){}*]/g, '')}%`, or use
`.ilike()` chained with `.or()` builder methods, or use a SQL RPC for the search.

## Needs Vivek review

Findings that touch product decisions or require deeper context:

- **#1 / #2 — Employee-actions role gates** (CRITICAL). Adding `await requireRole(['founder', 'hr_manager'])` at the top of `createEmployeeAccount` and `deactivateEmployee` is the obvious fix. But Vivek should also decide whether to log every creation attempt (success + failure) and whether to enforce that the email domain matches `@shiroienergy.com` for non-founder-created accounts. This is the kind of thing that warrants a 1-hr session.
- **#3 — process-document Edge Function auth**. Adding a webhook-secret check breaks the scripts/extract-existing-documents.ts backfill script. Vivek needs to decide whether the script gets a service-role JWT (current pattern in CLAUDE.md), a separate function-specific secret, or whether the function flips to require the service-role bearer in the Authorization header. The first option (service-role JWT) is cleanest but means anyone with a leaked service key can re-extract documents on demand.
- **#4 — /api/contacts/search auth**. Trivial to fix (add `await requireAuth()`), but the existing pattern across all `/api/*` routes is inconsistent — some routes auth, some don't, some rely entirely on RLS. Vivek should pick one rule: "every /api/* route either checks auth at the top OR documents why it doesn't." Worth a 30-min audit pass.
- **#5 — PostgREST .or() injection**. The fix is mechanical (sanitize the search term before interpolation), but doing it across 15 query files in one PR is error-prone. Suggest a tiny helper `escapeOrTerm(s)` in `@/lib/db-helpers.ts` and a Grep-driven sweep with code review.
- **#8 — Signed-URL TTL in proposal-sent event**. 30 days is too long. Suggest 7 days max, or sign just-in-time inside the n8n workflow's "send email" step rather than at event-emit time. Affects how n8n is wired — Vivek's call.
- **#10 / #13 — Field-level RLS for sensitive columns**. Postgres can't do per-column RLS, but we can use a VIEW (e.g. `channel_partners_safe`) that hides `bank_account_number`/`bank_ifsc` and route non-finance callers to it. Adds a maintenance burden — Vivek should weigh.
- **#14 — Client-vs-server masking convention**. Pick one (server-side masking via `maskSensitiveField`) and refactor `SensitiveField` to take a pre-masked string with a reveal-by-fetch button. Larger refactor; out of scope for a fix-up batch.
- **#17 — changePassword re-auth flow**. The current `signInWithPassword` pattern is documented but fragile. Add app-side rate-limiting (5 attempts per account per hour) to mitigate, and check whether Supabase has rolled out `reauthenticate()` to the JS client yet.
- **#18 — Internal PDF fetch with stripped cookies**. The current path works but is opaque. Refactor `sendProposalToCustomer` to call `assembleProposalPDFData` + `renderToBuffer` directly rather than HTTP-fetching its own endpoint. Same code, no internal HTTP round-trip.
